## 1. 背景与业务定位

真实业务链几乎都要登录态。一期采集已把凭证的下发与存放位置落库（凭证卡、credential_events 换票锚点、登录卡标注），但只是"记录"，无人"消费"。本需求让执行引擎消费凭证卡：注入登录态、过期自动换票。

**一句话业务定义**：执行时按凭证卡把 cookie/token 注入请求；命中 401 自动重登换票并重放原请求，全程无需人工。

**单列理由**（用户决策）：独立的安全风险面（凭证纪律）+ 独立的验收场景（过期换票），不并入 R-3。

## 2. 业务目标与价值

| # | 目标 | 衡量方式 |
|---|---|---|
| G1 | 带登录态链直跑成功 | 凭证按采集期记录的位置正确注入 |
| G2 | 凭证过期不中断 | 401 → 自动重登 → 换票 → 重放原请求成功 |
| G3 | 凭证纪律不破 | 运行记录/日志/路由响应中无凭证原文 |
| G4 | 换票失败诚实 | 重登失败如实报"需人工重新登录"，不静默伪造 |

## 3. 使用场景

1. **S1 带登录态直跑**：链中接口依赖会话 cookie，引擎按凭证卡注入后跑通。
2. **S2 隔天复跑换票**：凭证已过期 → 首请求 401 → 引擎按 credential_events 锚点重放登录卡链路换票 → 重放原请求 → 链继续。
3. **S3 换票失败**：登录卡也失效（密码改了/要验证码）→ 链中止，诊断明确"需人工重新登录并更新凭证卡"。

## 4. 功能需求

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-4.1 | 凭证注入：按一期凭证卡记录（`header:authorization` / `header:cookie:*` 等来源名）定位并注入真实值；注入点在请求构造（FR-3.2）之后、发出之前 | P0 |
| FR-4.2 | 401 检测与重登：命中 401 时按 credential_events 锚点重放登录卡链路，更新本地凭证后继续 | P0 |
| FR-4.3 | 原请求重放：换票成功后重放被 401 的请求，链不断 | P0 |
| FR-4.4 | 凭证零留痕：凭证值只在执行进程内过手，不入运行记录、不出路由、不进日志（沿用一期纪律，加扫描断言） | P0 |
| FR-4.5 | 换票失败语义：重登失败 → 链中止 + 明确诊断"需人工重新登录" | P0 |
| FR-4.6 | 换票节流：同一会话换票进行中时并发请求等待，不并发重登 | P1 |

## 5. 验收判据

- 带登录态链直跑成功，注入位置与采集期记录一致；
- 凭证过期场景专项测试：401 → 自动重登 → 换票 → 重放成功，全程无人工；
- 重登失败 → 诚实报错并标"需人工重新登录"；
- 对运行记录、日志、路由响应做凭证原文扫描：零命中；
- 并发节点同时遇 401 时只重登一次。

## 6. 依赖、风险与不做

- **依赖**：R-3 执行引擎；一期凭证卡/credential_events 落库（已交付）。
- **已知风险**：一期凭证收割以 cookie 为主，token 类（Authorization 头/localStorage 取 token 拼请求）覆盖度不足——若目标站是 token 型，本需求需先补一期采集能力（在设计期验证并如实上报）。
- **不做**：凭证的采集与录入（一期范围）；验证码/风控突破（诚实边界，如实失败）。
